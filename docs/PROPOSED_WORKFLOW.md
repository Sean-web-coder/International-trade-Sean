# TradeScout 目标流程草案

这是讨论稿；以用户最后确认的决策记录为准。新增 Codex skills 是开发与分析指南，必须将选定规则实现到网站代码和数据库后才会影响产品行为。

## 一位用户每天的工作

1. 选择阿联酋、沙特或南非，搜索家居、厨房、收纳、礼品相关的区域批发商和进口商；也可导入自己的 CSV。每天目标联系 15–20 家，因此候选池需要更大。系统按标准化公司域名去重，保留每次发现的来源与日期。
2. AI 给候选公司准备业务概况和六项评分证据，所有证据默认是“待审”。网页展示每项主张、来源网址及原文摘录。用户打开来源并逐项通过、驳回或标为待核实。仅通过的证据影响分数；没有公开中国采购证据时保留候选，但该项不加分。更改意见留下时间记录。
3. 对高匹配客户只保存公开可核查的工作邮箱，附来源和核查日期；缺少已核实邮箱则保留公司、不发信。邮件写作只引用经过用户批准、与收件人相关的事实。可证明的自身服务为义乌多品类找货、验货和拼柜/集运；不承诺未经确认的价格、MOQ、时效或交易成果。
4. 系统生成简短英文 Gmail 草稿，用户在 Gmail 中人工审核和发送。系统根据 Gmail 的真实发件消息记录首次联系时间、消息标识和所属会话。草稿创建不等于发信。
5. 发件后第 4 天和第 11 天，若未收到回复，工作台显示待办提醒并准备新的待审草稿；每天向用户自己的邮箱发送一封到期待办摘要。同步到任何回复则停止这家公司的后续提醒；用户决定接下来的销售动作，并记录询价、报价、样品、订单或输单原因。
6. 客户页保留时间线：发现、证据审批、联系人核实、草稿、实际发件、回复、跟进和销售阶段变更。邮件仅保存主题、时间、状态、会话链接和用户手写摘要，正文仍在 Gmail。按国家、状态和下一动作筛选，并提供合格客户→发信→回复→询价→订单的可追溯漏斗。导出完整可恢复备份。

## 系统约束

- Render 免费实例中的 SQLite 不满足长期保存。采用托管 PostgreSQL 和可恢复备份；旧数据如有，先只读导出，再验证导入记录数和关联关系。
- Gmail 个人账号的 OAuth 应在用户本人 Google Cloud 项目中配置。对草稿创建与收发同步分别申请所需的最小权限；Google 对测试模式、长期令牌和公开应用的当前政策需要在实现前核对。凭据与令牌只存在服务器端，绝不写进 GitHub、聊天或浏览器本地存储。
- 既有 Render Codex CLI 登录和实际模型搜索在用户账号下尚待验收；数据库和邮箱功能不能掩盖模型连接失败。
- 每日准时摘要与后台 Gmail 同步依赖可靠调度。用户接受必要的付费常驻网页/调度服务，实际产品、价格和购买步骤应在实施前核对；不自动购买。
- 不自动发邮件，也不抓取受限制或非公开的联系人。不同国家的营销邮件规则需在具体模板和发送流程中体现。
- 站点当前使用单工作台连接码；若要长期保存 OAuth 凭据和客户联系资料，应加登录保护、速率限制和令牌轮换。

## 拟分阶段验收

1. **基础可靠性**：真实 Codex 连通性；持久化数据库、迁移/备份恢复；公司去重和 CSV 导入。
2. **可信客户**：来源采集与安全校验、人工证据审批、重新计分、批量审核队列。
3. **邮箱闭环**：Google OAuth、创建草稿、发件与回复同步、活动时间线。
4. **跟进经营**：第 4/11 天提醒、回复停止规则、销售阶段和看板指标。

每阶段都要有能证明行为正常的测试和实际操作验收。部署费用和 Google 授权步骤须在购买或授权前明确；代码实施从用户确认这份整体设计后开始。

## 验收用例草案

- **数据**：创建客户、联系人、证据、草稿和活动后重启服务，记录仍在；执行备份并在空数据库恢复，数量和关联关系一致。
- **去重**：`example.com`、`www.example.com` 和同公司官网不同路径进入同一公司档案，原始来源仍可追溯。
- **证据**：模型声称“中国采购”且给出网址时，未审核该项分数为 0；用户驳回后仍为 0；批准可信来源后才得分，并记批准人和时间。
- **发信**：创建 Gmail 草稿后状态仍是“未发送”；只有同步到真实 Gmail 发件消息才变为“已发送”并设定跟进日期；无法核实邮箱时不提供发信动作。
- **回复**：同一 Gmail 会话收到回复后，不再生成第 4/11 天跟进草稿；历史发件、回复和人工阶段操作保留可查。
- **提醒**：未回复时到期任务仅出现一次；用户可以推迟、关闭或手工完成；不能向客户自动发送邮件。
- **经营**：筛选国家和日期后，客户数、获批数、实际发信数、回复数、询价数和订单数能够回溯到对应活动。
