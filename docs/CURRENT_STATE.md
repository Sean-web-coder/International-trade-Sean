# TradeScout 当前系统检查（2026-10-20）

这是对 `tradescout-windows` 分支现有代码的检查记录。业务目标和后续实现范围仍需用户逐轮确认。

| 环节 | 当前能做 | 关键缺口 |
| --- | --- | --- |
| 找客户 | 按国家、品类搜索官网候选；去除一次结果中的重复域名 | 未形成明确的目标客户画像和排除条件；没有跨批次公司去重、批量导入或搜索任务历史 |
| 背调 | Codex 搜索公司背景；按六项规则打 0–100 分并保存模型给出的来源 | `score_prospect` 只检查模型字段、解释和非空来源字符串，没有实际读取官网或核实来源是否支持断言；人工证据批准不存在 |
| 联系人 | 手工记录姓名和邮箱 | 没有邮箱有效性验证、联系人来源和核实时间 |
| 发信 | 生成首封和两封跟进英文邮件草稿；人工编辑保存 | 不连接邮箱；不能创建邮箱草稿、发送或记录真实发送结果；草稿中可引用未经人工核实的模型事实 |
| 跟进 | 手工更改一个客户状态 | 没有活动时间线、发信/回复同步、下一次跟进日期或提醒 |
| 数据 | 本地 SQLite、客户 CSV 导出、含邮件草稿的 JSON 导出 | Render 免费实例磁盘不持久；无备份导入；一条连接码可访问全部资料并触发 Codex 模型调用 |
| AI 连接 | 服务器 Codex CLI 设备码登录或本机连接器；模拟任务测试 | 尚无已核实的 Render 上真实模型研究请求完成记录 |

证据主要在 `engine.py`、`storage.py`、`web_server.py`、`web/index.html`、`tests/` 和 `WEB_DEPLOY.md`。

## 后续决策树

1. **客户目标**：目标国家、细分买家、产品范围和排除条件。决定搜索来源、字段和评分规则。
2. **证据标准**：官网/第三方证据如何核验、谁批准、何时复查。决定评分与发信中哪些事实可用。
3. **发信权限**：纯草稿、邮箱草稿或逐封确认发送。决定邮箱集成、授权和活动记录。
4. **数据与跟进**：持久化存储、团队人数、提醒方式。决定数据库与账户模型、任务时间线。
5. **具体节奏**：确认前四项后，再定开发信语言/长度、首封与跟进间隔、回复后的停止规则和指标。

## 已加入的 Codex 项目技能

- `prospecting`：定义目标客户画像、找线索和分层验证。
- `customer-research`：梳理客户需求、购买信号与证据。
- `cold-email`：写开发信、考虑送达与回复规则。
- `revops`：设计客户阶段、跟进活动与数据质量。

来源为 MIT 许可的 `coreyhaines31/marketingskills`。这些文件在 `.agents/skills/`，作为 Codex 开发与分析时的指南；它们不是网站中的运行时插件。要让网站按选定规则工作，需要在确认业务方案后将规则实现到应用代码中。
