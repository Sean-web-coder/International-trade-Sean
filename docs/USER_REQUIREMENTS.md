# Sean 的外贸全流程系统需求说明书

版本：1.0  
整理日期：2026 年 10 月 20 日（北京时间）  
用途：作为以后重建、迁移或扩展系统的独立需求输入。新开发者或新的 AI 会话应先阅读本文件，不应要求用户重新回答已确认的问题。

## 1. 我的核心目标

我需要一个适合自己业务的外贸系统，把寻找客户、公司背调、证据审核、开发信、跟进、销售阶段和效果统计串起来，并长期保存客户资料和业务记录。

我希望直接打开网址就能操作，配置尽量由开发者完成。我不熟悉下载项目、解压 ZIP、运行脚本或维护本机连接器；以前这些步骤多次阻碍使用。因此，交付应包含真实可访问的网址、必要的一次性授权引导和可操作的验收步骤，不能只交源码路径或压缩包。

我的 AI 要求是使用我自己的 Codex CLI 和 Codex 订阅额度。不要未经同意改成另外收费的 OpenAI API Key 方案。是否能在具体托管环境使用我的账号，必须以官方允许的登录方式和真实模型请求验证。

## 3. Codex 接入与使用体验

### 必须满足

1. 网页能发起获客、背调和邮件辅助任务，调用我授权的 Codex。
2. 使用我的 Codex 订阅账号；没有额外 API 费用的授权时，不自动切换为 API 计费。
3. 账号密码只在官方授权页面输入。不要让我把密码、Cookie、OAuth 令牌或密钥发到聊天里。
4. 页面应区分未登录、已登录、正在执行、实际调用成功、调用失败等状态。
5. 验收需要一次真实模型响应。网页能打开、服务健康、连接器在线、CLI 已登录或模拟测试通过，都不能替代实际调用成功。
6. 我希望网站直接使用，不希望日常依赖本机连接器窗口一直打开。

### 实现方式的区别

我最初提出调用 Windows 本机上的 Codex CLI，之后强调网页直接使用。原系统因此准备了“在我自己的服务器上运行官方 Codex CLI，并由我完成 ChatGPT 账号设备授权”的实现。

服务器 CLI 使用服务器上的登录状态，不等于远程控制我电脑上的 Codex。重建时应明确实际采用哪种方式，并以账号权限、平台兼容性和真实测试为准，不得承诺未经验证的订阅可用性。

## 4. 客户发现与导入

1. 支持公开网页搜索，并可按国家、产品范围和买家类型查找。
2. 支持导入我自己的 CSV 表格。
3. 候选公司必须有可追溯的来源网址及发现日期。
4. 同一公司的官网域名、www 变体和不同网址路径应正确去重；重复发现保留来源信息，不重复建立客户档案。
5. 搜索结果只是候选，不等于已经核实或可以发信。
6. 每日 15–20 家是合格客户联系目标。系统应支持足够大的候选池和高效审核队列。

## 5. 背调、证据审批与评分

1. AI 提供公司概况、业务模式、品类、批发／进口相关线索和对应公开来源。
2. 证据默认“待审核”，显示具体主张、来源网址和可核对的摘录；没有摘录时不得编造。
3. 由我逐项通过或驳回，也可保留待核实状态。
4. **只有我通过的证据才能计分。AI 自己写 confirmed=true 不算人工确认。**
5. 审批应留下时间与操作记录，便于查看更改原因及复查。
6. 没有可信“中国采购”证据时，继续保留候选，该项不给分；不得因此断言对方不从中国采购。
7. 邮件个性化只引用我已经通过的事实。
8. 证据内容被重新生成或实质修改后，应重新审核，避免旧审批自动覆盖新内容。

## 6. 联系人和工作邮箱

1. 只使用官网或其他公开可核实的工作邮箱，也接受我提供的可核实资料。
2. 保存邮箱来源网址和核实日期。
3. 不猜测联系人姓名，不编造或推算邮箱。
4. 找不到可核实邮箱时，保留公司资料，等待补充联系人；暂不提供可发送的邮件草稿。
5. 公司、联系人、邮箱和核实记录应关联，避免向错误公司或重复联系人发信。

## 7. Gmail 与邮件流程

1. 我使用个人 @gmail.com，愿意按步骤配置 Google Cloud OAuth 并亲自授权。
2. 系统在 Gmail 中创建可审阅草稿，由我在 Gmail 中审核和发送。
3. **不自动向潜在客户发信，不自动群发。**
4. 自动同步相关邮件的真实发送状态及客户回复。
5. 创建草稿不能把客户标记为已联系，也不能开始跟进倒计时。
6. 只有检测到实际发件事件，才记录发送时间和启动跟进计划。
7. Gmail 原邮件留在 Gmail。CRM 只长期保存关联邮件的主题、时间、发件状态、会话链接和我手写的摘要；不复制整个邮箱或长期保存所有邮件原文。
8. Google 授权过期、撤销或同步失败时，页面要明确提示，不能把同步中断当成客户没有回复。

### 原项目邮件规则：作为默认实现参考

原项目要求英文邮件主题不超过 6 词、正文不超过 50 词、纯文本、无附件、不编造恭维或事实，并提出一个容易回答的问题。原模板署名为 Sean。

这些属于原项目规则，重建可作为默认值，但不能把它们误写成这次访谈中逐项新确认的要求。正式使用前应允许核对署名和发件人资料。

## 8. 跟进与销售管理

1. 首封邮件实际发送后，第 4 天和第 11 天进行未回复跟进。
2. 到期时显示提醒并生成可审阅的新草稿，仍由我人工发送。
3. 收到任何回复后停止该客户后续的自动跟进提醒与草稿生成，交由我判断下一步。
4. 工作台显示到期任务，每天向我自己的邮箱发送一封待办摘要。这是内部提醒，不是自动向客户发信。
5. 客户流程需跟踪到：回复、询价、报价、样品、订单，以及输单原因。
6. 第一版暂不扩展到出货、回款和完整 ERP。
7. 客户页应有活动时间线，关联发现、审核、草稿、实际发件、回复、跟进和销售阶段变更。

第 4／11 天的业务规则已确认；时区、每日摘要发送时间、工作日调整、自动回复识别与同公司多联系人处理等细节尚未单独确认，应在需要时提出具体默认方案。

## 9. 数据长期保存与访问

1. 客户资料、联系人、证据、审批、邮件元数据和跟进记录必须长期保存。
2. 服务重启、重新部署或应用升级后，业务数据不应丢失。
3. 支持导出、备份与恢复；备份必须经过恢复验证，不能只有下载按钮。
4. 迁移旧系统时先备份，再核对导入记录及关联关系，不丢失草稿、来源或审批记录。
5. 第一版是我的私人工作台，需保护客户资料、Gmail 授权和 Codex 额度。
6. 凭据不要写入 GitHub、日志、聊天或公开页面。
7. 如果 Codex 在服务器运行，登录凭据的持久化需独立处理，不能以“数据库已持久化”代替“Codex 登录已持久化”。

## 10. 看板与目标衡量

看完整转化漏斗，不只看发信数量：

- 合格客户；
- 实际发信；
- 回复；
- 询价；
- 订单。

支持按国家和时间筛选，能从指标追溯到客户与活动记录。合格客户判定阈值、公司数与邮件数的统计口径应在实现中明确，避免重复计数。

## 11. 预算与托管

1. 我接受付费托管数据库。
2. 我接受必要的常驻网站运行和定时任务费用，以支持稳定同步和每日摘要。
3. 实际购买前，要列明具体服务、套餐和实时费用，供我审核。
4. 我接受必要费用不等于授权购买任意套餐，也不等于已经绑定或开通了服务。
5. Render 是当前选择；PostgreSQL 是原方案的技术选型。重建时可以提出更适合的方案，但必须满足长期保存、可靠调度、易使用和成本可解释。

## 12. 分阶段交付与验收

| 阶段 | 交付范围 | 关键验收 |
|---|---|---|
| 1 基础可靠性 | 真实 Codex 调用、持久化数据库、迁移、备份恢复、去重、CSV 导入 | 真实模型响应；重启数据不丢；备份能恢复；重复公司不重复建档 |
| 2 可信客户 | 证据展示、逐项审批、重新计分、审核队列 | 待审与驳回均不得分；通过才加分；未通过事实不进入邮件 |
| 3 邮箱流程 | Gmail OAuth、草稿、真实发件和回复同步、活动记录 | 草稿不算发件；实际发件启动计时；回复正确关联客户 |
| 4 跟进与经营 | 第 4／11 天提醒、每日内部摘要、销售阶段、转化看板 | 回复后停止；重复执行不重复生成；指标能追溯 |

每阶段都应说明：代码完成了什么、本地测试了什么、线上真实验证了什么，以及哪些外部授权或配置尚未完成。不得把这些状态混为一谈。
